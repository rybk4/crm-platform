# Правила фронтенда CRM

Обязательны для всех, кто пишет код в `crm/` — людей и ассистентов.
Правило, которое нельзя проверить машиной, всё равно проверяется на ревью: PR с нарушением не мёржится.

Стек зафиксирован: **React 19 + TypeScript + Vite + MUI + React Router + TanStack Query + axios**.
Новые библиотеки добавляются только после обсуждения — «я привык к этой» не аргумент.

---

## 1. Структура

```
src/
  app/          — корневой App, роутинг верхнего уровня
  lib/          — код, не знающий о предметной области CRM
  modules/      — бизнес-модули
  ui/           — обёртки над MUI, собственный дизайн-кит
```

**Модуль** — это вертикальный срез предметной области (`auth`, `specialists`, `services`, `clients`, …):

```
modules/<module>/
  api/<module>Api.ts      — класс-наследник ApiClient
  api/<module>Keys.ts     — ключи запросов TanStack Query
  components/             — компоненты (только разметка)
  components/<module>.css — стили модуля
  hooks/                  — состояние и логика
  model.ts                — чистые функции предметной области
  types.ts                — типы модуля
```

`model.ts` — это правила без React и без сети: значения формы по умолчанию, преобразование ответа сервера в форму, сборка payload, валидация, форматирование. Всё, что туда попало, обязано быть покрыто юнит-тестами.

Правила зависимостей, нарушать нельзя:

- `lib/` **не импортирует** ни `modules/`, ни `ui/`. Это чистые утилиты: http, i18n, хранилище токенов, валидация.
- `ui/` **не импортирует** `modules/`. Дизайн-кит ничего не знает о специалистах и услугах.
- `modules/` импортируют `lib/` и `ui/` свободно.
- Модуль **не лезет в `components/` чужого модуля**. Разрешено брать у соседа `api/`, `hooks/`, `model.ts` и `types.ts` (как «Услуги» берут `useSpecialists`). Нужен чужой компонент — переноси его в `ui/` или в общий модуль.
- Циклы между модулями запрещены.

Новый раздел CRM = новый модуль + запись в `modules/shell/navigation.ts` + тип в `modules/shell/types.ts` + маршрут в `AppShell`.

## 2. Размер файлов и разделение разметки и логики

**Лимиты:**

| Тип файла               | Мягкий лимит | Жёсткий предел |
| ----------------------- | ------------ | -------------- |
| Компонент (`.tsx`)      | 150 строк    | 200            |
| Хук, api, utils (`.ts`) | 200 строк    | 300            |
| Любой файл              | —            | 300            |

Превысил — дели, а не проси исключение. Файл на 300 строк почти всегда означает, что в нём живут две разные вещи.

**Разметка отдельно от логики. Это главное правило проекта.**

Компонент в `components/` — это функция, которая получает данные и возвращает JSX. В нём допустимо:

- вызовы хуков (`useLocale`, свой `use<Module>` и т. п.);
- `map` по данным для рендера;
- тернарники и `&&` для условной разметки;
- однострочные обработчики, пробрасывающие событие дальше: `onClick={() => onEdit(specialist)}`.

В компоненте **запрещено**:

- `fetch`, вызовы `*Api.*`, `authenticatedRequest`;
- `try/catch` вокруг запросов, `notifications.*` по результатам запросов;
- бизнес-правила (валидация формы, нормализация payload, вычисление расписания);
- `useState`/`useEffect` для серверных данных;
- функции длиннее 5 строк внутри JSX-файла.

Всё это уезжает в `hooks/use<Something>.ts` рядом с модулем. Эталон — `modules/auth/hooks/useAuthFlow.ts`: экран `AuthScreen` не знает ни про токены, ни про ошибки API, он только раскладывает переданное по разметке.

Компонент-страница выглядит так:

```tsx
export function SpecialistsPage({ activeBranch }: SpecialistsPageProps) {
  const { t } = useLocale()
  const { specialists, isLoading, dialog, save, remove } = useSpecialists(activeBranch)

  return ( /* только JSX */ )
}
```

Локальное UI-состояние (открыт ли попап, какая вкладка активна, значение фильтра в инпуте) может жить в компоненте — это разметка, а не логика. Состояние формы, которая уходит на сервер, живёт в хуке.

Чистые функции форматирования (`formatPrice`, `initials`) выносятся в `lib/format/` при повторном использовании; пока они нужны одному модулю — держим наверху его файла, до 5 строк.

## 3. Компоненты

- **Только именованные экспорты.** `export default` в проекте нет и не будет.
- Компонент — `function`-декларация, не `const` со стрелкой:
  ```tsx
  export function Button({ children }: ButtonProps) {} // да
  export const Button = ({ children }: ButtonProps) => {} // нет
  ```
- Пропсы — `interface <Component>Props`, объявлен прямо над компонентом, не экспортируется без нужды.
- Пропсы деструктурируются в сигнатуре, значения по умолчанию задаются там же: `kind = 'primary'`.
- Один компонент — один файл, имя файла = имя компонента (`PhoneStep.tsx`). Исключение: `Text.tsx` держит `Heading` и `Text` — родственную пару. Больше двух в файле не собираем.
- Хуки вызываются только на верхнем уровне компонента (`react/rules-of-hooks` в oxlint включён как `error`).
- Порядок импортов, разделённый пустой строкой: внешние пакеты → `@/lib` → `@/ui` → соседние модули → относительные внутри модуля → `./*.css` последним.

## 4. TypeScript

- `any` запрещён. Его сейчас нет ни в одной строке проекта — так и держим. Для неизвестного — `unknown` и сужение типа (см. `parseApiErrors`, `readTokens`).
- Приведение `as` — только там, где TS физически не может вывести тип (`data as T` после `response.json()`). `as any`, `as unknown as X`, `!` без причины — нет.
- `import type` для всех типовых импортов — включён `verbatimModuleSyntax`, иначе не соберётся.
- Типы ответов бэкенда описываются **в snake_case, как их отдаёт Django**: `phone_number`, `active_branch_details`, `duration_minutes`. Не переименовываем на клиенте — расхождение имён дороже, чем непривычный стиль.
- Тип payload выводим из типа сущности, а не пишем руками:
  ```ts
  export type SpecialistInput = Omit<
    Specialist,
    'id' | 'branch_name' | 'full_name' | 'services_count'
  >
  ```
- Строковые множества — `as const` + вывод типа, не `enum`:
  ```ts
  export const supportedLocales = ['ru', 'en', 'kk'] as const
  export type Locale = (typeof supportedLocales)[number]
  ```
- `noUnusedLocals` и `noUnusedParameters` включены. Мёртвый код не коммитим.

## 5. Импорты и алиасы

Внутри модуля — относительные пути (`../api/servicesApi`, `./PhoneStep`).
Всё, что за пределами модуля, — через алиас `@/`:

```ts
import { ApiError } from '@/lib/api/http'
import { useLocale } from '@/lib/i18n/LocaleContext'
import { Button } from '@/ui/Button'
import { specialistsApi } from '../api/specialistsApi'
```

`../../../` в импортах больше не проходит ревью.

## 6. UI-кит и MUI

**MUI импортируется только внутри `src/ui/`.** В `modules/` и `app/` не должно быть ни одного `import ... from '@mui/material'`. Сейчас это выполняется на 100% — правило защищает нас от того, что смена MUI на что-то другое потребует правки каждой страницы.

Нужен новый контрол MUI — сначала обёртка в `src/ui/`, потом использование. Обёртка:

- принимает узкий набор собственных пропсов, а не прокидывает `...props` наружу;
- использует наш словарь вариантов, а не MUI-шный: `kind="primary" | "quiet" | "outline" | "danger"`, а не `variant="contained"`;
- не тащит наружу типы MUI.

`@emotion/styled` в проект не добавляем, хоть он и лежит в зависимостях как транзитивный для MUI.

## 7. Стили

- Стили — обычный CSS в файлах рядом с компонентами: `modules/<module>/components/<module>.css`, `ui/<component>.css`. Импортируется последней строкой импортов.
- Именование — BEM: `.specialist-row`, `.specialist-row__avatar`, `.form-grid--three`. Без вложенности глубже одного уровня, без `#id` в селекторах.
- **Цвета, шрифты, отступы — только через CSS-переменные темы:** `var(--app-surface)`, `var(--app-border)`, `var(--app-primary)`, `var(--app-font-family)`. Хардкод `#2563eb` в CSS модуля — ошибка: в проекте 9 тем, и захардкоженный цвет сломает восемь из них.
- Новый токен добавляется сразу в три места: `AppThemeDefinition['tokens']` в `ui/theme/themes.ts`, во **все** темы, и в `themeVariables` в `ui/UiProvider.tsx`.
- `style={{ ... }}` в JSX — только для действительно динамического значения, которое нельзя выразить классом (образец: `style={{ backgroundColor: color }}` в `ThemeStudio`). Во всех остальных случаях — класс.
- `!important` — нет. Единственное исключение уже в коде (`module-empty-state`), новых не добавляем.
- Состояния описываем через `data-`атрибуты, а не через нагромождение классов: `data-active={specialist.is_active}`, `data-sidebar-collapsed={collapsed}`.

## 8. i18n

**Ни одной пользовательской строки в коде.** Всё через `t('key')`. Это касается и `aria-label`, и `title`, и текста в `window.confirm`.

- Ключи живут в `lib/i18n/messages.ts`, три локали: `ru`, `en`, `kk`.
- Добавил ключ в `ru` — **обязан** добавить в `en` и `kk` в том же коммите. `TranslationMessages` типизирован по `ru`, так что пропуск не соберётся — не обходи это через `Partial`.
- Ключи в camelCase, сгруппированы по разделу: `specialistsTitle`, `specialistsEmptyDescription`, `errorPhoneFormat`.
- Подстановки — через `{name}`: `servicesCount: 'Услуг: {count}'` + `t('servicesCount', { count })`.
- Для «1 специалист / 5 специалистов» заводим отдельные ключи (`specialistsCount`, `specialistsCountOne`) — так уже сделано.
- Язык в запросы к API уходит заголовком `Accept-Language` автоматически (`lib/api/http.ts`), руками его ставить не надо.

## 9. Работа с API

Весь обмен с бэкендом идёт через один клиент. **`axios` импортируется только внутри `lib/api/`** — так же, как MUI только внутри `ui/`. В `modules/` не должно быть ни одного `import axios`.

`lib/api/httpClient.ts` — единственный экземпляр axios. Он сам:

- подставляет `Authorization: Bearer <access>` и `Accept-Language`;
- ловит 401, обновляет access-токен через `/api/auth/token/refresh/` и повторяет исходный запрос **один раз**;
- сводит параллельные 401 к одному запросу обновления — остальные ждут его результат;
- при неудавшемся обновлении чистит токены и сообщает через `lib/auth/session`, после чего слой авторизации переводит на экран входа;
- поднимает и снимает флаг недоступности сервера;
- превращает любую ошибку в `ApiError` с разобранными сообщениями бэкенда.

`lib/api/ApiClient.ts` — база, от которой наследуются API всех модулей. Наследник объявляет базовый путь и методы предметной области:

```ts
class SpecialistsApi extends ApiClient {
  constructor() {
    super('/api/specialists/')
  }

  list(options?: { signal?: AbortSignal }) {
    return this.get<Specialist[]>('', options)
  }

  create(input: SpecialistInput) {
    return this.post<Specialist>('', input)
  }

  update(id: number, input: SpecialistInput) {
    return this.put<Specialist>(`${id}/`, input)
  }

  remove(id: number) {
    return this.delete(`${id}/`)
  }
}

export const specialistsApi = new SpecialistsApi()
```

- Наследник — единственный способ ходить в сеть. Свой `axios.create`, `fetch` или голый `apiHttp` в модуле — ошибка.
- Методы `get/post/put/patch/delete` защищённые: наружу торчат только методы предметной области. Типы axios за пределы `lib/api` не выходят.
- Экспортируется **готовый экземпляр** (`export const specialistsApi = new SpecialistsApi()`), а не класс: состояния у него нет, а единый объект удобнее в мутациях.
- Публичные эндпоинты (вход по коду, обновление токена) помечаются `{ anonymous: true }` — им не нужен токен и не нужен рефреш по 401.
- Пути всегда со слешем на конце: `/api/specialists/${id}/`. Django редиректит иначе, и POST теряет тело.
- Токены читаются **только** через `lib/auth/tokenStorage`. `localStorage.getItem('...')` с ключом токена в коде страниц — запрещено.
- Классы в `api/` не ловят ошибки, не показывают тосты и не знают про i18n. Они бросают `ApiError` — обработка выше.
- Инфраструктурные запросы, не принадлежащие ни одному модулю (проверка здоровья сервера), живут в `lib/api/`, а не в `modules/`.

Бэкенд отдаёт две проверки: `GET /api/health/` — готовность (проверяет БД, отвечает 503, если она недоступна) и `GET /api/health/live/` — живость процесса. Обе без авторизации. Фронтенд и docker healthcheck опрашивают `/api/health/`.

## 10. Данные и состояние (TanStack Query)

Серверные данные живут в TanStack Query. Ручные `useState` + `useEffect` + `try/catch` для загрузки списков — больше не пишем.

- Ключи запросов строим централизованно, в `modules/<module>/api/<module>Keys.ts`, и всегда включаем в ключ то, от чего зависит выборка (например, активный филиал):
  ```ts
  export const specialistKeys = {
    all: ['specialists'] as const,
    list: (branchId: number | null) => [...specialistKeys.all, 'list', branchId] as const,
  }
  ```
- Запрос и мутации оборачиваются в хук модуля, компоненты `useQuery` напрямую не вызывают.
- `queryFn` пробрасывает `signal` в API: `({ signal }) => specialistsApi.list({ signal })`. Иначе устаревший запрос продолжает висеть после ухода со страницы.
- После успешной мутации — `invalidateQueries` по ключу, а не ручной `reload()`.
- Данные и форма — разные хуки. `use<Module>` держит запросы и мутации, `use<Module>Dialog` — состояние формы и отправку. Страница вызывает оба и остаётся разметкой.
- Клиентское состояние (открытые диалоги, черновики форм, фильтры) в Query не кладём — это `useState` в хуке модуля.
- Глобальных стейт-менеджеров (Redux, Zustand, MobX) в проекте нет. Нужно общее состояние — контекст рядом с владельцем данных, как `LocaleProvider` и `UiProvider`.

## 11. Ошибки и уведомления

Единая схема, отступать нельзя:

1. `lib/api/http.ts` бросает `ApiError` с разобранными сообщениями бэкенда.
2. Хук модуля ловит и показывает: `notifications.error(error instanceof ApiError ? error.message : t('errorUnexpected'))`.
3. Компонент про ошибки запросов ничего не знает.

- Тосты — только через `lib/toast/notifications`. Прямой `import { toast } from 'react-toastify'` вне этого файла запрещён.
- Успех операции тоже подтверждаем тостом: `notifications.success(t('specialistCreated'))`.
- Ошибку валидации формы показываем на поле (`error` + `helperText` у `TextField`), а не тостом. Тост — для ответов сервера.
- `console.log` в коммитах нет. `console.error` — только в местах, где ошибку больше некому показать.

### Падение рендера

Приложение не должно показывать белый экран. За это отвечает `AppErrorBoundary` в `src/app/`, он обёрнут вокруг всего `App` в `main.tsx` и рисует карточку «что-то пошло не так» с кнопками «Повторить» и «Обновить страницу». Сбрасывается сам при смене маршрута.

- Примитив `ui/ErrorBoundary` — единственный класс-компонент в проекте, так и должно быть: ловить ошибки рендера умеют только классы.
- Отдельный boundary вокруг раздела ставим, только если падение раздела не должно уносить остальной интерфейс. Сначала — общий.
- Текст ошибки (`error.message`) показываем пользователю только в `import.meta.env.DEV`.
- Боундари не ловит ошибки в обработчиках событий и в промисах — там по-прежнему `try/catch` и `notifications.error`.

### Недоступность сервера

- `lib/api/serverStatus.ts` — единственный источник правды. `http.ts` сам поднимает флаг при сетевой ошибке и 502/503/504 и снимает его на любом успешном ответе. Руками статус нигде больше не трогаем.
- 401, 403, 400 и 500 недоступностью **не считаются**: это ответы работающего сервера, их показывает обычный тост.
- Плашку рисует `modules/shell/components/ServerStatusBanner`, логику держит `useServerStatus`: пока флаг поднят, хук опрашивает `/api/health/` раз в 5 секунд и снимает его, как только сервер ответил.
- Плашка не блокирует интерфейс — пользователь не должен терять заполненную форму из-за моргнувшей сети.
- Проверка здоровья ходит мимо `httpRequest` намеренно: иначе её собственный сбой снова поднимал бы флаг и проверка зациклилась бы.

## 12. Тесты

**Всё новое покрывается тестами.** PR с новой логикой без тестов не принимается.

Инструменты: **Vitest + @testing-library/react + jsdom**. Файл теста лежит рядом с тестируемым кодом: `useAuthFlow.test.ts`, `phone.test.ts`.

Что тестируем обязательно:

- любая функция в `lib/` — юнит-тестом на входы/выходы, включая граничные случаи (`normalizePhone('8705…')`, `parseApiErrors` с вложенным объектом);
- любой хук модуля — рендером через `renderHook`, с замоканным `api/` слоем;
- любая бизнес-логика: валидация, сборка payload, преобразование данных сервера в форму (`toForm`, `defaultSchedule`).

Что тестируем по необходимости:

- компонент — если у него есть ветвления разметки или доступность, которую легко сломать (`AuthScreen` по стадиям, состояние empty/loading/список). Проверяем поведение, видимое пользователю, а не структуру DOM.

Чего не делаем:

- не тестируем обёртки `ui/`, которые просто пробрасывают пропсы в MUI;
- не мокаем `fetch` вручную там, где достаточно замокать модуль `api/`;
- не пишем снапшот-тесты разметки — они ничего не ловят и всё время краснеют.

Правило «разметка отдельно от логики» существует в том числе ради этого: логика в хуках тестируется без рендера и без DOM.

## 13. Доступность

Не опционально, уже заложено в коде:

- у каждой иконочной кнопки — `ariaLabel` (переведённый);
- декоративные `svg` — `aria-hidden="true"` и `focusable="false"` (так сделано в `Icon`);
- у форм — настоящие `<form onSubmit>` и `<label>` через `id`/`name` у полей, а не «div с onClick»;
- фокус после навигации переводится на `<main>` (см. `AppShell`), ссылка `skip-link` работает;
- статусные области — `role="status"` + `aria-live="polite"`;
- всё, что кликается, должно работать с клавиатуры. `onClick` на `div` — ошибка.

## 14. Форматирование и проверки

Форматирование делает Prettier, спорить о нём не надо:

```json
{ "semi": false, "singleQuote": true, "printWidth": 100, "trailingComma": "all" }
```

Отсюда следует то, что и так есть в коде: без точек с запятой, одинарные кавычки, отступ 2 пробела, висящие запятые.
JSX-элемент с более чем тремя пропсами разносится по строкам — Prettier сделает это сам.

Перед коммитом обязаны проходить:

```bash
npm run format:check   # prettier
npm run lint           # oxlint
npm run build          # tsc -b && vite build
npm test               # vitest
```

Красный CI не мёржится. Отключать правило линтера построчно (`// oxlint-disable-next-line`) можно только с комментарием, объясняющим причину.

## 15. Мелочи, о которых спорят

- Ключ в списке — стабильный `id` сущности (`key={specialist.id}`). Индекс массива — только для строк формы, у которых ещё нет id, и тогда `key={certificate.id ?? index}`.
- `window.confirm` для удаления — временное решение. Новый код использует `Dialog` из `ui/`.
- Отладочные подсказки бэкенда (`response.debug` в OTP) показываются только как есть, никакой логики вокруг них.
- В `localStorage` ходим **только** через `lib/browser/storage`: в приватном режиме и при запрете на хранение данных прямое обращение бросает исключение и роняет приложение на старте. Ключи — с префиксом и версией: `crm.auth.tokens.v1`, `crm.locale.v1`, `crm.theme.v1`. Прочитанное значение всегда валидируем по форме, а не доверяем ему.
- Пустое состояние раздела — через `ui/ModulePage` или `management-empty`, а не «ничего не отрисовали».
- Файл `src/assets/react.svg`, `vite.svg` и прочий шаблонный мусор Vite можно и нужно удалять, когда он перестаёт использоваться.

## 16. Долг

Пусто. Все файлы укладываются в лимиты, логика вынесена из разметки, серверные данные живут в TanStack Query, сеть — за единым клиентом.

Сюда попадает только то, что осознанно отложено, с указанием файла и плана. Правило прежнее: трогаешь файл из списка — приводишь его в порядок в том же PR. Список не должен становиться складом «потом разберёмся».

Не покрыто тестами по-прежнему многое из разметки — это нормально: требование действует на новый и изменяемый код, а не на разовую догонку.
